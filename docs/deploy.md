# Установка

Пошагово, с нуля до работающего сервиса. Занимает минут пятнадцать, из них
десять — заполнение `.env`.

Сервис ставится **рядом с ботом, на тот же сервер**: он ходит в webapi бедолаги
по внутренней docker-сети, наружу этот порт открывать не нужно.

## Что нужно заранее

- Бот bedolaga версии **3.52.0 или новее**, работающий в docker (проверено на
  4.0.0). На более ранних нет `GET /pages/faq`, и база знаний останется пустой.
- Доступ в админку бота — оттуда берётся сервисный токен.
- Ключ OpenAI либо совместимый шлюз.
- Группа в Telegram с топиками, куда сервис будет писать, что он сделал.
  Формально необязательна, но без неё вы не увидите ни одного его решения.

## 1. Токен к API бота

В админке бота: **Web API → Токены → создать**. Скопируйте значение сразу,
второй раз его не покажут.

> Токен не разграничен по правам: он даёт полный доступ к webapi бота, включая
> изменение балансов и подписок. Сервис пользуется только чтением тикетов,
> ответом и приоритетом, но сам токен — секрет уровня «доступ к боту».

## 2. Имя docker-сети бота

Сервис должен оказаться в одной сети с ботом:

```bash
docker inspect <контейнер_бота> -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}'
```

Обычно это `remnawave-bot_default`. Запомните вывод — он пойдёт в `BOT_NETWORK`.

Имя контейнера бота, если не помните: `docker ps --format '{{.Names}}'`.

## 3. Забрать репозиторий и заполнить настройки

```bash
git clone https://github.com/AirP0WeR/bedolada-support.git
cd bedolada-support
cp .env.example .env
nano .env
```

Минимум, без которого сервис не стартует:

```ini
BEDOLAGA_API_URL=http://remnawave_bot:8080   # имя контейнера бота и его порт webapi
BEDOLAGA_API_TOKEN=<токен из шага 1>
OPENAI_API_KEY=<ключ>
LLM_MODEL=gpt-5.6-luna
```

Очень желательно — наблюдение, иначе сервис работает вслепую:

```ini
TG_BOT_TOKEN=<токен отдельного бота-наблюдателя>
TG_CHAT_ID=-1001234567890
TG_TOPIC_ID=42
BRAND_NAME=Название сервиса     # как модель называет вас в ответах
```

`TG_CHAT_ID` — id группы (у супергрупп начинается с `-100`), `TG_TOPIC_ID` —
id топика: откройте нужный топик в вебе, последнее число в адресе.

И имя сети из шага 2:

```ini
BOT_NETWORK=remnawave-bot_default
```

`AI_REPLY_ENABLED` не трогайте: `false` — это правильное начальное значение.

## 4. Каталог состояния

Контейнер работает не от root, поэтому каталог с базой должен принадлежать
пользователю контейнера:

```bash
mkdir -p data && chown 1000:1000 data
```

Здесь будут лежать `state.db` (что сервис уже отвечал и эскалировал) и кеш
FAQ. Каталог должен переживать пересоздание контейнера — иначе сервис забудет,
в каких тикетах он уже был.

## 5. Проверить связность до запуска

```bash
docker compose run --rm support-ai python -m app.main --check
```

Проверяются по очереди настройки, API бота, база знаний, модель (одним
коротким запросом) и топик наблюдения — в него придёт тестовое сообщение.
Вывод выглядит так:

```
[   OK   ] Настройки: всё заполнено, режим теневой — клиенту не пишем
[   OK   ] API бота: доступен, активных тикетов 4
[   OK   ] База знаний: 8214 символов
[   OK   ] Модель: gpt-5.6-luna ответила, потрачено 2317 токенов
[   OK   ] Наблюдение: тестовое сообщение отправлено — проверьте топик

Готово к запуску: docker compose up -d
```

Не проходит — смотрите «Если что-то не так» в конце.

## 6. Запуск в теневом режиме

```bash
docker compose up -d
docker compose logs -f
```

Сервис начнёт разбирать тикеты и писать в топик черновики с пометкой
«клиенту не отправлен». Клиент при этом не получает ничего — всё работает
ровно как до установки.

## 7. Когда включать боевой режим

Не по времени, а по накопленным черновикам. Разумные критерии:

- набралось **не меньше 30–50 черновиков** на живых обращениях;
- среди них **нет ни одного выдуманного факта** — цены, сроки, инструкции,
  которых нет в базе знаний (это единственная по-настоящему дорогая ошибка);
- то, что модель отдала оператору, вы бы тоже отдали оператору;
- суточная сводка (`DIGEST_HOUR`) не показывает всплесков ошибок модели.

Если черновики регулярно врут — это чинится базой знаний, а не порогом:
допишите недостающее в FAQ бота или в `kb/`.

Когда устраивает:

```bash
sed -i 's/^AI_REPLY_ENABLED=.*/AI_REPLY_ENABLED=true/' .env
docker compose up -d
```

Первые дни держите `MAX_AI_REPLIES=1`: сервис отвечает один раз, а если клиент
переспросил — тикет уходит человеку.

## Обновление

```bash
cd bedolada-support && git pull
docker compose pull && docker compose up -d
```

База знаний из `kb/` подхватывается перезапуском, без пересборки образа.

## Откат

У каждого коммита есть неизменяемый тег образа:

```bash
IMAGE=ghcr.io/airp0wer/bedolada-support:sha-1a2b3c4 docker compose up -d
```

Состояние в `data/` переживает откат: сервис не ответит второй раз в тикеты,
где уже отвечал.

## Выключить

Погасить ответы клиентам, оставив наблюдение:

```bash
sed -i 's/^AI_REPLY_ENABLED=.*/AI_REPLY_ENABLED=false/' .env && docker compose up -d
```

Остановить совсем: `docker compose stop`. Тикеты просто копятся и ждут людей.

## Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| `network remnawave-bot_default not found` | Неверный `BOT_NETWORK`, см. шаг 2 |
| `API бота: HTTP 401` | Токен недействителен или отозван, создайте новый |
| `API бота: Connection refused` | Неверный `BEDOLAGA_API_URL` — нужны имя контейнера бота и порт webapi, не публичный адрес |
| `unable to open database file` | Каталог `data/` не принадлежит uid 1000, см. шаг 4 |
| `База знаний: пуста` | В админке бота нет активных страниц FAQ на языке из `KB_LANGUAGES` |
| `Модель: … (ключ, шлюз или имя модели)` | Проверьте `LLM_MODEL` по `GET /v1/models` вашим ключом |
| Сервис молчит, в логах пусто | Все тикеты отсеиваются воротами — это нормально, если их ведут люди |
| В топик ничего не приходит | Бот-наблюдатель не добавлен в группу или не имеет права писать в топик |

Логи: `docker compose logs -f --tail 200`. Состояние контейнера, включая
healthcheck: `docker compose ps`.
